Local places

Plan an easier day out

Help someone find a place that suits their plans and access needs.

Who are you helping?

Imagine a person with a free afternoon who wants somewhere enjoyable, affordable, and easy to get around.

What will you make?

A simple page that lets them compare a few places by cost, indoor or outdoor setting, and access notes.

What information can you use?

The demo already has a place list in src/data.js. Its names and details are examples, not verified local advice.

Things you could try

  • Think about one person and what would make a day out easier for them.
  • Try showing the example places as clear, readable cards.
  • Explore one helpful control, such as “free places” or “indoors”.
  • Invite a teammate to try it and notice what might be clearer.

A useful outcome

Someone can find a place that suits them, see why it might work, and use the main controls with a keyboard.

Want to take it further?

Add live weather for a chosen location using the Open-Meteo weather service. Keep the example list as a fallback and show when the weather was checked. The basic request does not need a key; check the current terms before use.

Give Codex this first prompt
You are helping my hackathon team make a simple day-out planner. First inspect the project and explain which files control the page and the sample places. Do not change files yet. Then suggest the smallest first change: show the places as clear cards with their cost and access notes. We are beginners, so use plain HTML, CSS, and JavaScript, keep the page keyboard-accessible, and do not connect to another website yet.

Public data

Make numbers make sense

Help someone understand how one public number changes over time.

Who are you helping?

Imagine someone who has seen a statistic in the news and wants to understand what it actually says.

What will you make?

A small explainer that lets them choose a place, compare years, and see a plain-language summary of the pattern.

What information can you use?

Start with the practice dataset. Its numbers are invented for this exercise. The live-data stretch links to the official source.

Things you could try

  • Explore the dataset headings and what each number and year means.
  • Try letting someone choose a place and see its values over time.
  • Consider a comparison or short explanation, while keeping the original numbers visible.
  • See how a teammate interprets the pattern and whether any context would help.

A useful outcome

Someone can choose a place, see how its number changes, and tell the data apart from your explanation.

Want a harder version?

Fetch population data from the World Bank public data service. It does not require a key. Show the indicator name, source, and year so people can check what the numbers represent.

Want to add an AI helper?

Prototype a chat box that answers questions about the numbers currently on screen. The supplied demo is a mock, not a live AI. Never put a real model key in this public website.

Give Codex this first prompt
Help my team build a simple public-data explainer. First inspect the project and the file data/population-sample.csv. Explain what a row and column mean in plain language; do not edit yet. Then suggest a first screen where a person chooses a place and compares its values by year. Keep the source and the fact that these are practice numbers visible. Use plain HTML, CSS, and JavaScript, and do not connect to a live website yet.

Reusable design

Make public information easier to use

Create a small set of reusable design parts, then use them to help someone compare local places.

Who are you helping?

Imagine someone scanning several local options on a phone and trying to spot what matters to them.

What will you make?

A simple place list and a tiny design system: shared colours, text styles, spacing, and reusable place cards or labels.

What information can you use?

Use the example places already in src/data.js. You can sketch the visual rules in Figma or go straight to code.

Things you could try

  • Decide which three facts might help someone compare places.
  • Experiment with reusable rules for colour, text size, spacing, and keyboard focus.
  • Try a place card and a useful label, then see where else they could be reused.
  • Explore how the cards work on a phone and for people who do not distinguish every colour.

A useful outcome

The cards make the same information easy to compare, and your team can explain the design rules behind them.

Want a harder version?

Create the colour and text styles as Figma variables, then use Figma MCP to bring the design context into Codex. MCP is an optional connection between an AI tool and another service; ask a facilitator for setup help.

Give Codex this first prompt
Help my team turn the example places into a clear, reusable interface. First inspect the project and explain where its colours and spacing are defined. Do not edit yet. We want to define a small set of design tokens, make one reusable place card, and use it for every place. Keep the page readable, keyboard-accessible, and easy to use on a phone. Explain changes in beginner-friendly language.

CGI and career growth · advanced

Build your CGI growth story

Track your skills and work examples to see where you are growing and plan what to learn next. Use the information to build your personal development plan or prepare for a review or promotion conversation.

Who are you helping?

You: a CGI product designer who wants to make your skills, progress, and next steps more visible.

What will you make?

A tracker for your skills and confidence, with room for work examples, learning goals, and opportunities. Use it to draft a personal development plan, year-end review, or promotion-deck outline.

What information can you use?

Start with your skills, confidence levels, work examples, and learning interests. Public sources such as World Economic Forum skills trends and the UK Digital and Data capability framework can help you look for broader trends. They do not set CGI’s expectations. Use client or bid information only if you have approval.

Things you could try

  • Reflect on the skills you use now and the ones you want to build; note your own confidence level for a few of them.
  • Add examples of your work or feedback that show how you have used those skills, at a level you are comfortable sharing.
  • Track a learning goal, useful learning opportunities, and progress over time.
  • Explore a dashboard, timeline, or summary that could help you shape your personal development plan, review, or promotion story.

A useful outcome

You can update your skills and work examples, then use them to plan a development goal or draft a career summary. The page makes clear which points come from you and which are AI suggestions.

Want a harder version?

Turn the draft review into a promotion-deck outline, using a structure supplied by your facilitator if one is available. The exercise does not include CGI’s official promotion format. Do not invent achievements or use real review, client, or bid information in an unapproved AI tool.

Suggest the smallest useful screen for recording my skills, self-assessed confidence, examples of work, and one learning goal, then shaping a draft year-end review outline from information I enter. Do not invent skills, achievements, or evidence. Keep my information separate from AI suggestions. Use plain HTML, CSS, and JavaScript, and do not connect to internal CGI systems or a live AI service.

Optional add-on for any project

Add a small design system

Once one screen works, choose a few colours, type, and spacing rules for it. An hour is enough for a first pass on one part of your project.

Route 1: Make your own

Choose this route if you want to learn how a design system works. In Figma, make a page with colour and text styles, spacing steps, and a button, card, and label. In the website, create matching CSS variables and reusable styles in styles.css.

  1. Choose a small set of colours, type sizes, spacing, and corner shapes.
  2. Build one button, one information card, and one label.
  3. Use them on your screen, then adjust them together in Figma and code.
Copy a prompt to start your own 
Help us create a tiny design system for this project, not a full company-wide system. First inspect the existing HTML and CSS and explain what is already there. Then suggest a small set of accessible colour, type, spacing, and focus tokens, plus three reusable parts we need for this screen. Keep it in plain HTML and CSS. Show us the proposed rules before changing files, and explain how we can mirror the same names in Figma variables.

Route 2: Start from an existing system

Choose this route if you want ready-made components. Pick one library so the setup stays manageable.

  • Open Props gives you ready-made CSS variables for things like colour, type, and spacing. It is a useful token foundation; you still design your own page and components.
  • Web Awesome gives you ready-made web components that can be used from ordinary HTML. Its official guide supports a CDN start, which avoids a build setup; the team needs internet access.

For this one-day event, try Open Props to work with tokens or Web Awesome to assemble a screen from existing components. If neither fits, keep using the starter’s CSS.

Copy a prompt to use an existing system 
Help us improve this screen using [Open Props / Web Awesome]. First check the official documentation and inspect our current HTML and CSS. Explain what the library gives us and what we still need to design. Propose the smallest change that reuses it without changing our plain HTML, CSS, and JavaScript setup. Keep the data and interactions working, and check keyboard focus and mobile layout.

For the CGI project, start with EDS

If you have access, start with the CGI Enterprise Design System (EDS). Use its approved components, styles, and guidance where they fit. Ask a facilitator for the matching Figma library, and check CGI policy before connecting internal files to an AI tool.

Want to connect Figma and Codex?

Make a Figma page with named variables and components, then ask Codex to use it as context. Figma MCP can share selected frames, components, and variables. Ask a facilitator to help set it up, and test the connection before the event. Availability and usage limits depend on your Figma plan and seat. Your team still needs to check that the code fits the design and works for people with different access needs.

What your team does next

  1. Choose one project. You do not have to build all four.
  2. Talk before you code. Agree who the project helps and what they need to do.
  3. Ask Codex to explain the starter. Open the project folder, paste the prompt from your project, and ask it to explain anything unclear.
  4. Build one small part. Check it in a browser. Keep what works and fix what does not.
  5. Show your learning. At the end, share the prototype, what the AI helped with, and one thing your team had to check or decide.
In a team of four or five

Share the jobs across the team. Someone can keep the user problem in view, another can sketch the flow, and others can focus on data, Codex, keyboard checks, or the demo. Pair up where it helps; the jobs can overlap.

Before you build together

Get your own copy and work as a team

GitHub keeps the shared project online. GitHub Desktop lets you clone it, save changes, and share them with the team. You can follow this guide without using Terminal.

Starter repository: github.com/uxsw/hackathon-starter-kit

1

Get ready

Create a GitHub account if you do not have one. Install GitHub Desktop and sign in. If you are new to GitHub, you can first try its built-in practice tutorial.

2

Make one shared copy for your team

Open the starter repository link above. One teammate can click Fork on GitHub to make a team copy, then invite the others as collaborators in the repository settings. If the organiser has already made a team repository and invited you, use that one. Ask a facilitator if you are unsure.

3

Download it with GitHub Desktop

In GitHub Desktop, choose File → Clone Repository, select the team repository, choose where to save it on your computer, and click Clone. GitHub Desktop downloads a working copy. Open that folder in Codex and follow the setup notes to view the page.

4

Start a branch before making changes

A branch holds one set of changes. In GitHub Desktop, choose Current Branch → New Branch, give it a short name such as skill-tracker or place-cards, and create it. Each person should use a separate branch. Try not to edit the same file at the same time.

5

Fetch, save, and share your work

Before you start, click Fetch origin to check for teammates’ latest updates. After a change, review the files in GitHub Desktop and add a short summary. Click Commit to… to save it, then Push origin or Publish branch to share it online.

6

Open a pull request

A pull request (PR) asks to add your branch’s changes to the team’s main version. In GitHub Desktop, choose Preview Pull Request or Create Pull Request. Check that the base is your team’s main branch and the compare branch is yours. Add a sentence about your changes and create the PR on GitHub. Ask a teammate to review it, then merge it when you are ready. Switch back to main in GitHub Desktop, click Fetch origin, then Pull origin to get the merged changes.

If something looks wrong: pause before clicking buttons such as “Discard changes.” GitHub Desktop shows what changed; a facilitator can help sort out conflicts or a branch that is behind.

Optional: share your prototype

Publish it with GitHub Pages

GitHub Pages can publish this plain HTML, CSS, and JavaScript project at a public web address. View this starter kit online. To publish your team’s own version, first push the finished files to your team repository. On GitHub, open Settings → Pages. Under Build and deployment, choose Deploy from a branch, select main and /(root), then save. When it has finished publishing, GitHub shows the site link in the same Pages settings area. It can take a few minutes to appear.

Anything published there can be viewed by other people. Use sample data and never publish passwords, API keys, or private information.
